When a workflow failed, see if there is an attached artifact with a name that ends with `.patch`, and try to apply it on the branch, in a new commit.

### Functionality Details

This module automates the process of applying patch files generated by CI workflows. When a workflow fails and produces a `.patch` artifact, the module will:

- Download the `.patch` artifact from the failed workflow run.
- Attempt to apply the patch to the target branch, which is the branch of the workflow run unless the artifact
  name asks for another one, see [Targeting another branch](#targeting-another-branch).
- Commit the changes with a message based on the patch filename or a default message.
- Push the commit to the pull request branch, allowing the workflow to re-run with the proposed fix.

If the target branch is protected (e.g. `main`) and the direct push is rejected by GitHub, the module will automatically:

- Reuse the open `ghci/patch/<target-branch>-*` pull request whose head commit was created by the patch module,
  by force pushing the new commit on its head branch, so a scheduled workflow does not open a new pull request
  on every run. A pull request with a head commit pushed by somebody else is never reused.
- Otherwise create a new branch named `ghci/patch/<target-branch>-<run-id>`.
- Push the commit to the new branch.
- Open a pull request targeting the protected branch with auto-merge enabled.

This helps contributors and maintainers quickly test and apply automated fixes suggested by CI jobs.

### Targeting another branch

A scheduled workflow runs on the default branch, but the changes it produces can belong to another branch: a
`matrix` over the stabilization branches, for example the `.po` files refreshed from the running instances of
every supported version. For that case the artifact name can carry the target branch:

```text
<message> [<branch>].patch
```

The `<message>` part is used as the commit message and as the pull request title, and the patch is applied on
`<branch>` instead of the branch of the workflow run. The artifacts of a single run are grouped by target
branch: one worktree, one push and one pull request per branch.

Because a patch produced by a pull request workflow must never land on another branch than the pull request
one, the override is only honoured when the workflow run event is listed in the `patch.branch_override_events`
setting (`GHCI__PATCH__BRANCH_OVERRIDE_EVENTS`), which defaults to `schedule`, `workflow_dispatch` and
`repository_dispatch`. An artifact asking for another branch on any other event is skipped and reported in the
check output summary.

```yaml
on:
  schedule:
    - cron: '0 3 * * *'

permissions:
  contents: read

jobs:
  l10n:
    strategy:
      matrix:
        branch: [prod-2-9, prod-2-10]
    steps:
      - uses: actions/checkout@v5
        with:
          ref: ${{ matrix.branch }}
      ...
      - run: git add --all
      - run: git diff --staged --exit-code
        id: diff
      - run: git diff --staged --patch > /tmp/l10n.patch
        if: failure() && steps.diff.outcome == 'failure'
      - uses: actions/upload-artifact@v4
        with:
          name: Update the l10n files [${{ matrix.branch }}].patch
          path: /tmp/l10n.patch
          retention-days: 1
        if: failure() && steps.diff.outcome == 'failure'
```

The workflow no more needs a personal access token to push a branch and to create the pull request: it only
uploads an artifact, and the module pushes with the GitHub application permissions.

### Loop protection

If the CI fix is unstable (for example a non-deterministic `pre-commit`), each new commit can make the
workflow fail again, produce a new patch, and so on, resulting in an infinite loop of commits.

To avoid that, the module refuses to apply a new patch when:

- The last `patch.max_consecutive_commits` commits (default: `10`) of the branch were all created by the
  patch module (identified by the commit message trailer `From the artifact of the previous workflow run`), or
- For a protected branch, there are already `patch.max_consecutive_commits` open `ghci/patch/<branch>-*`
  pull requests created by the patch module.

In that case the module fails with an explanatory summary and does not touch the branch. The counter is
reset as soon as an other commit is pushed on the branch (or the pending pull requests are closed or merged).
The limit can be configured with the `patch.max_consecutive_commits` setting
(`GHCI__PATCH__MAX_CONSECUTIVE_COMMITS`).

### Usage in the workflow

```yaml
on:
  pull-request:

jobs:
  <name>:
    steps:
      ...
      - run: git diff --exit-code --patch > diff.patch
      - uses: actions/upload-artifact@v4
        with:
          name: <commit_message>.patch
          path: diff.patch
          retention-days: 1
        if: failure()
```

### Usage Notes

- Ensure the workflow produces a valid `.patch` file as an artifact on failure.
- The artifact must contain exactly one file, the patch itself.
- The module will only attempt to apply patches if the artifact is present and can be cleanly applied.
- Review the resulting commit to ensure the patch does not introduce unintended changes.
